# Changelog

## Unreleased

- Prepared multi-store search. `palace.multistore.prepare_store_search` makes every pre-provider refusal of a multi-store search, then its query expansion and embedding calls, including the vector leg's pool and dimension bounds (now checked after every security check and before any provider work, with their existing texts), and returns an immutable `PreparedStoreSearch` that holds no connection or provider. `execute_prepared` admits the stores again, searches their current rows with the prepared vectors, and reranks once. It refuses a changed recorded identity, embedder or vector-backend selector, published index or configured reranker, and never embeds or expands. `search_stores` is now exactly the two steps, with unchanged results and refusal texts (a vector-leg bound can now pre-empt a non-security refusal for a request that is invalid twice over); on success each provider receives the same calls, inputs and order. Expansion and embedding now all happen before the first vector query, so failure paths differ: an expansion, no-term or embedding failure refuses before any S3 Vectors request, while a failure that can occur only during retrieval now follows embeddings a single search would have skipped. Constructed query providers close when preparation returns.
- Prepared single-store search. `palace.search.prepare_search` admits one store without constructing any provider, then makes the matching entry point's expansion and embedding calls in its order, and returns an immutable sealed `PreparedSearch`; `execute_prepared_search` admits the store again, refuses a changed identity, selector, published index or reranker, or a database that appeared or vanished, searches the current rows with the prepared vectors and reranks after its snapshot closes. `search`, `search_expanded`, `rerank_candidates` and `search_reranked` are now exactly the two steps, with unchanged signatures, results and refusal texts; on success each provider receives the same calls, inputs and order, while query embedding and expansion now happen before the retrieval snapshot opens, so on failure provider calls can differ, as for the multi-store seam. The configured reranker's preflight (local checks only, no request) now runs at preparation and again at execution. The private `_reranker_config` parameter of `rerank_candidates` is removed.
- Returned-hit evidence. `evidence=True` on `prepare_search`, `prepare_store_search` and `search_stores` attaches one `palace.prepared.HitEvidence` per returned hit to `RerankedSearch.evidence` and the new `MultiStoreSearch.evidence`, read in the retrieval's own snapshot on every return path: the exact stored body, body hash, embedding-input digest and vector bytes when `verified`, or a closed status (`remote-only`, `missing-local-row`, `body-hash-mismatch`, `missing-vector`, `malformed-vector`, `missing-input-digest`) for that one entry. It refuses `mode="bm25"`. See `docs/multi-store.md` for its limits.

## 0.4.1 — 2026-11-11

- The `bedrock` embedding provider admits a Bedrock API key supplied through the AWS SDK's `AWS_BEARER_TOKEN_BEDROCK` variable when no SigV4 credentials resolve. The SDK signs both the same-Region `GetAccountDataRetention` read and `InvokeModel` with the token, and prefers it over credentials when both are present. The retention check is unchanged and still mandatory: the key must also be authorized to read the account's retention mode, and a denied read or any mode other than `none` refuses before the first embedding request. A set-but-blank token variable, or one outside the RFC 6750 bearer-token syntax (for example with a trailing newline, which the HTTP library would echo in its error), now refuses before any request without showing the value, and token values are redacted from Bedrock error messages. Signing is proved offline with synthetic values; server-side acceptance of a real key is not.
- The declared minimum is now `boto3>=1.43.26`. Earlier SDK releases (including the previously declared 1.39.9 floor, through 1.43.25) lack the `GetAccountDataRetention` operation the provider requires, so the old floor could install an environment that could never pass the retention check. Installers pinned below 1.43.26 must upgrade; the locked resolution is unchanged at boto3/botocore 1.43.104.

## 0.4.0 — 2026-11-09

- Explicit finite byte budgets above the unchanged 64 MiB file-vector snapshot default, with the existing hard row ceiling. Optional `commit_plan(snapshot_limits=FileVectorLimits(...))` admits the staged snapshot within the existing transaction and rolls back an oversized publication; callers verify the committed snapshot with the same budget before acceptance.
- Explicit caller-supplied embedding representations and ordered input views for full per-file plans, with transactional exact-input digests. Existing breadcrumb inputs remain the default. The caller owns rendering, filename policy and fresh filename embedding; changing representation requires rebuilding incompatible derived state.
- Bounded `read_file_vectors` snapshots of one nominated committed file, including chunk/vector rows, complete embedding identity, input digests and an actual file-view digest. Composition holds one same-store writer lock through connection close. Cross-store copying preserves input evidence; removal deletes it atomically.
- The Conric runtime requirement names its published v0.1.0 tag; the lockfile retains the same resolved source commit.

## 0.3.0 — 2026-11-07

- A registered `bedrock` embedding provider for Cohere Embed v4 (`cohere.embed-v4:0`) on a direct regional Bedrock runtime endpoint: the AWS SDK credential chain only, a fail-closed same-Region `GetAccountDataRetention` check requiring `none` before the first request, `search_document` and `search_query` input types, batches of at most 96 inside a conservative 120,000-unit request budget, Palace-owned audited retries with SDK retries and endpoint-URL overrides disabled, and identity `bedrock:<region>`. It requires a published-corpus assertion. As of 2026-11-07, one bounded workstation-profile run in one Region with a synthetic ten-note corpus passed; instance-role authentication, other Regions, throughput and real-corpus behaviour are not established. See `docs/bedrock.md`.
- Composed settings: `palace.settings` validates a top-level `palace` section of a Conric composition through the same validator as the TOML selector, and initializes a store's selector once, refusing a different existing selector. `palace providers set --settings FILE` (repeatable) is the command-line entry point. Selector refusals now share one reason table and name the field path.
- Per-store vector width: `chunks_vec` is declared at the store's selected dimension, readers compare the recorded dimension with the declared width, and a store whose table was created at another width is refused with a rebuild remedy. Existing 4096 stores keep byte-identical DDL.
- Embedders are resolved for an explicit `document` or `query` purpose; the Python `resolve_embedder` requires the `purpose` keyword. Callers parsing `embed_batching` see `per-turn(max=96,budget=120000)` for Bedrock.
- Conric is a Git-pinned runtime dependency; the release and CI procedures export hash-locked requirements without it and install it from the pinned commit.

## 0.2.0 — 2026-10-21

- Fair, bounded synchronous indexing across large and small documents, durable source- and embedding-identity-bound receipts, atomic completed-document visibility, and structured progress. Existing chunk text, embedding inputs and provenance remain unchanged.
- Declared admission limits visibly refuse oversized sources, tails, plans and chunks before inference. The Python API exports `BuildLimits` and `BuildProgress`; the former soft chunk-window constant is removed. These changed pre-1.0 contracts require a minor release. Limits are engineering choices, not measured throughput, memory or cost guarantees.
- Interrupted builds reuse compatible work. A changed frozen source or corrupt receipt refuses with a recovery remedy; no automatic corrupt-receipt deletion or online embedding-generation swap is provided.
- The indexing daemon parks at its first failed event and retains the last successful checkpoint, so later events cannot move the cursor past a failed update. Remedy and explicit restart remain operator actions.
- Remote embedding requests respect the conservative aggregate request budget, while preserving request order, input bytes, audit and provenance semantics.
- Test-only native watcher proof hardening and storage error propagation corrections, plus clearer project introduction.
- Upgrading from 0.1.0: the default ordinary-source/unconsumed-JSONL-tail limit is 8 MiB, with 16,384 changed chunks per document, a 64 MiB serialized plan, 100,000 files per invocation and 1 GiB logical staging. One over-limit source refuses the whole synchronous build before inference, including deletion reconciliation and identity certification; a JSONL file over 8 MiB also refuses `--full` because it starts at offset zero. Single inputs over 128 KiB raw now refuse; OpenRouter inputs must additionally fit its 30,000 conservative normalized-byte/framing-unit budget. The CLI has no limit flags: narrow or ignore sources, or deliberately adjust `BuildLimits` through Python. Existing rows remain visible on admission refusal.
- Callers parsing `embed_batching` must handle the new `per-turn(...)` labels. Local and private HTTPS builds use at most 32 inputs per turn; OpenRouter uses at most 1,024 under its request budget. Derived receipts live in `index/build-staging`; daemon state can report `park_kind: work-failure`. The Python `build_root` entry point requires a file-backed database.
- Synthetic upgrade qualification with an injected deterministic embedder: a store created by the published 0.1.0 wheel remains searchable and its unchanged incremental build is a no-op under 0.2.0; canonical source bytes are preserved. Real provider identities and operator stores are not certified.
- Clean exact-wheel installation and synthetic synchronous indexing/retrieval are qualified on macOS ARM64 and Linux ARM64. Package-registry publication, production inference, Linux daemons and other architectures remain separate.

## 0.1.0 — 2026-09-30

- Published vector indexes: a store opted in as published publishes its chunk vectors to an Amazon S3 Vectors index incrementally by chunk key (puts before deletes, a receipt that avoids listing the index), and can select that index as its vector search leg; every S3 Vectors request is audited and counted.
- Per-file store operations: `palace index copy` moves named files' rows between stores without embedding, `palace index remove` deletes named files, and a keyword-row lookup lets every per-file operation find a file's keyword rows without reading the whole keyword table.
- Concurrent index writers: a per-store writer lock the operating system releases with its holder, taken by builds, the daemon, per-file updates and metadata batches; stale plans are re-planned rather than committed; `palace index update` reflects named files without walking the tree.
- Exact indexed document metadata, atomic replacement/deletion, paginated document lookup and metadata-constrained retrieval without corpus reembedding.
- Local-first file/event memory substrate with rebuildable lexical and vector retrieval.
- Explicit store indexing and complete embedding identity checks.
- Origin-preserving multi-store retrieval with one merged rerank.
- Explicitly authorized private HTTPS embedding and reranking, credential references, bounded requests, audit and no provider substitution.
- Synchronous macOS ARM64 and Linux ARM64 qualification; macOS-only watcher and service boundaries remain explicit.
- MIT release preparation, scoped archives and clean-install verification. Publication and stable compatibility remain owner decisions.

Personal retrieval evaluation, additional private/cloud adapters and production deployment qualification remain separate work.
